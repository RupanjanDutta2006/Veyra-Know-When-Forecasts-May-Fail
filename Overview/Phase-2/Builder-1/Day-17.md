# Phase 2 — Builder 1 — Day 17
## End-to-End Integration + Upstream Efficiency Hardening

---

## 1. Objective

The primary objective of Day 17 is to resolve the upstream Open-Meteo request amplification limitation identified during Day 16 multi-horizon visual timeline testing by:
1. Implementing a **bounded, short-lived in-memory forecast cache** (`BoundedTTLCache`).
2. Implementing **concurrent in-flight request deduplication** (`SingleFlight` / Flight Coalescing).
3. Preserving strict **`DATA_UNAVAILABLE` abstention integrity** when upstream provider quotas or networks fail.
4. Implementing bounded **HTTP 429 `Retry-After` header inspection**.
5. Validating end-to-end integration and request count reduction from 7–16 upstream HTTP calls down to **1 single shared fetch**.
6. Executing automated regression suites and preparing manual browser verification test cases.

---

## 2. Starting State & Day 16 Carry-Forward

On Day 16, the **Visual Forecast Risk Timeline** was successfully integrated into the frontend dashboard, enabling users to evaluate forecast bust probabilities across medium-range lead horizons (24h to 384h).

However, multi-horizon timeline generation exposed a **request amplification** pattern:
- **Single Target**: 1–2 upstream HTTP calls.
- **Standard 7-Day Timeline**: 7–14 upstream HTTP calls (with retries).
- **Full 16-Day Timeline**: 14–28 upstream HTTP calls (with retries).

### Root Cause
Because `OpenMeteoGEFSWeatherService` previously had no weather response caching or concurrent request deduplication, every concurrent horizon request (`Promise.allSettled` across 7 or 16 lead times) independently queried Open-Meteo for the exact same 16-day forecast dataset. This rapid burst of identical queries exhausted the public Open-Meteo rate limit, resulting in HTTP 429 errors.

## 3. Architecture & Minimal Fix Design

```
Frontend Visual Risk Timeline (7 or 16 horizons)
                      ↓
POST /v1/predict (x7 to x16 concurrent requests)
                      ↓
OpenMeteoGEFSWeatherService.get_forecast()
                      ↓
[Step 1] Check BoundedTTLCache (TTL: 120s, maxsize: 512, keyed by deterministic query URL)
         ├── Cache HIT  → Return deep-copied cached raw JSON (< 0.1ms)
         └── Cache MISS → Proceed to In-Flight Deduplicator
                      ↓
[Step 2] SingleFlight Deduplicator (Flight Coalescing)
         ├── Request #1 (Leader)   → Acquires flight lock → executes single HTTP fetch
         └── Requests #2..N (Followers) → Await Request #1's Event completion
                      ↓
[Step 3] Leader fetch completes:
         ├── Success → Stores raw JSON in BoundedTTLCache → Wakes followers → All return identical dataset
         └── Failure → DOES NOT poison cache → Wakes followers → All safely abstain (DATA_UNAVAILABLE)
                      ↓
[Step 4] Parse canonical records with location metadata & run Quality Control
                      ↓
Feature Pipeline → ML Inference (0.280 threshold) → Safety Evaluation → API Response
```

## 4. Short-Lived Forecast Cache Implementation

A bounded, thread-safe LRU cache with time-to-live expiration (`BoundedTTLCache`) caches successful raw JSON forecast payloads from Open-Meteo:

- **Bounded Size**: Default `512` entries (configured via `WEATHER_CACHE_MAX_SIZE`).
- **Short TTL**: Default `120` seconds (configured via `WEATHER_CACHE_TTL_SECONDS`).
- **Deterministic Cache Key**: The complete canonical query URL generated by `build_query_url(latitude, longitude, target_date)`, containing:
  - `latitude` and `longitude`
  - `hourly` variables (`temperature_2m,surface_pressure,wind_speed_10m,relative_humidity_2m,precipitation`)
  - `models` (`gfs_seamless`)
  - `timezone` (`UTC`)
  - `wind_speed_unit` (`ms`)
  - `start_date` / `end_date` (if target date filtering is applied)
- **Coordinate Isolation**: Distinct coordinates (e.g., Kolkata `22.5726, 88.3639` vs London `51.5074, -0.1278`) generate distinct keys and never collide.
- **Fail-Safe Poisoning Prevention**: HTTP exceptions (429, 500, timeouts) are **never cached**, allowing subsequent requests to retry when network availability restores.

---

## 5. In-Flight Request Deduplication (`SingleFlight`)

To prevent the "thundering herd" problem where 7 to 16 concurrent timeline requests arrive simultaneously before the first request populates the TTL cache, a thread-safe `SingleFlight` deduplicator is implemented:

- **Leader-Follower Coordination**: The first request for a given cache key registers an active flight and executes the upstream HTTP request. All concurrent followers for the same key block on a `threading.Event`.
- **Atomic Cleanup**: The in-flight key is popped from the internal map in a `finally` block on both success and exception, guaranteeing zero memory leaks or deadlocks.
- **Shared Propagation**: If the leader succeeds, all followers receive the result. If the leader encounters an exception, all followers safely catch the exception and abstain with `DATA_UNAVAILABLE`.
- **Deep Copy Isolation**: Retrieved cached dictionaries are deep-copied on access to prevent mutation side-effects between concurrent callers.

## 6. HTTP 429 & Retry Hardening

In `backend/app/core/http_retry.py`:
- `execute_with_retry` now inspects the `Retry-After` response header when catching `urllib.error.HTTPError` with status code 429.
- If `Retry-After` is present, the sleep duration is bounded to a strict maximum of `2.0` seconds (`MAX_RETRY_AFTER_CAP_SECONDS`), preventing unbounded server thread blocking.
- When retries are exhausted, the exception is cleanly raised and converted by `SafetyEvaluator` into:
  ```json
  {
    "abstain": true,
    "risk_level": "UNKNOWN",
    "trust_state": "UNAVAILABLE",
    "reason_codes": ["DATA_UNAVAILABLE"]
  }
  ```
